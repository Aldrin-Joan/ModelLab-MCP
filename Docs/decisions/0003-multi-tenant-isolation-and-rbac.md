# ADR-0003: Multi-Tenant Data Isolation, Scoped RBAC, and Sliding-Window Rate Limiting

## Status
Accepted

## Date
2026-09-19

## Context
ModelLab is designed as a shared ML experimentation platform serving multiple teams, projects, and autonomous AI agents. Without robust tenant isolation, access controls, and rate limits:
- One tenant or rogue agent could access, overwrite, or delete proprietary datasets or model artifacts belonging to another tenant.
- A high-frequency agent loop could overwhelm the system with write mutations or expensive training jobs, starving other users (noisy-neighbor problem).
- Audit trails required for regulatory compliance (who trained what model on which dataset version) would be absent.

## Decision
Implement a defense-in-depth security model across three layers:

### 1. Multi-Tenant Data Isolation
- **Relational Data**: Every entity table in PostgreSQL (`projects`, `datasets`, `dataset_versions`, `experiments`, `runs`, `artifacts`, `audit_events`) enforces a mandatory `tenant_id` column. All queries filter strictly on `tenant_id`.
- **Object Storage**: S3 object keys are structured as `s3://<bucket>/tenants/{tenant_id}/experiments/{experiment_id}/...`. Presigned URLs generated by `get_experiment_predictions` and `read_experiment_artifact` enforce tenant boundaries.

### 2. Scoped Role-Based Access Control (RBAC)
- Tokens carry a `Principal` identity comprising `principal_id`, `tenant_id`, `role`, and explicit `scopes`.
- Available roles: `Viewer`, `Researcher`, `Operator`, `Admin`.
- Granular scopes:
  - `projects:read`, `projects:write`
  - `datasets:read`, `datasets:write`
  - `models:read`
  - `experiments:create`, `experiments:read`, `experiments:cancel`
  - `artifacts:read`
  - `audit:read`
- Every tool defines a `ToolPolicy` specifying the exact `required_scope` enforced by middleware before execution.

### 3. Layered Sliding-Window Rate Limiting
- Rate limits are tracked in Redis using an atomic Lua sliding-window script keyed by `{tenant_id}:{principal_id}:{category}`.
- Tool categories have distinct per-minute thresholds:
  - `read`: 120–300 req/min (low cost)
  - `metadata`: 60–120 req/min (moderate cost)
  - `experiment`: 10–120 req/min (high cost - queueing training jobs)
  - `analysis`: 20–60 req/min (computational diagnostics)
- Requests exceeding limits immediately return `ResourceLimitExceededError` with HTTP 429 semantics and increment OpenTelemetry counter `rate_limit_denials_total`.

## Consequences
- **Positive**:
  - Complete tenant isolation: tenants cannot view or manipulate other tenants' projects, datasets, or experiments.
  - Granular least-privilege agent credentials (e.g. read-only evaluator agent vs experimenter agent).
  - Rate limiting protects Redis queues and worker pools from runaway agent loops.
- **Negative / Trade-offs**:
  - Requires Redis connectivity for rate limit checking on every MCP tool call.
  - Benchmark runners and automated pipelines must be configured with appropriate rate limits (e.g. `RATE_LIMIT_EXPERIMENT_PER_MINUTE=120`).
